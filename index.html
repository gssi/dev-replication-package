Investigating Developers’ Soft-Ethical Preferences in the Age of LLM-Based Coding Assistants

Different implementations can meet the same requirements while carrying different ethical implications. This study investigates the choices developers retain, the values those choices express, and how to make their preferences explicit when delegating code generation to LLMs.

What is a soft-ethical implementation preference? A preference among valid implementation alternatives left open by requirements and legal, organizational, and technical constraints. These choices can shape both source code and the behavior users experience.

RQ1 · Developer’s agency

Discretion remains. Values influence the choices.

Developers report room for judgment after requirements and constraints are defined. They delegate some of that judgment to coding assistants, while seeking to retain control through prompting and code review.

Survey participants and recruitment

The survey collected 104 responses from software practitioners across 23 countries, excluding the four survey pilot participants. We used purposive sampling to target developers currently working in industry; participants could also hold research roles.

We recruited through Prolific (75 respondents), direct invitations (25), and developer communities on Reddit (4), with all channels leading to the same Google Form. Prolific screening restricted participation to people currently employed in software engineering or development, experienced in programming, and familiar with programming languages. Prolific participants received $2.50; participation through the other channels was voluntary and uncompensated. Responses were anonymized before analysis.

Participants worked primarily in private companies (76%). Most were software developers or engineers (53.8%) or senior developers (27.9%), and 83.7% had at least three years of professional experience. They represented diverse development areas and application domains, particularly backend and full-stack development (51.9% each), finance, and developer tools (26–28%).

RQ1 · Three answers

  • Answer #1. Developers report substantial discretion over implementation choices affecting both code structure and observable software behavior, including choices with potential soft-ethical implications.
  • Answer #2. Developers report considering personal priorities and soft-ethical aspects when making discretionary implementation choices. While some developers explicitly recognize the ethical relevance of their decisions, others may make choices that reflect such aspects without explicitly recognizing their ethical implications. Such decisions are often context-dependent, with application domain and intended users influencing developers’ priorities.
  • Answer #3. Developers report delegating discretionary implementation choices to LLM-based coding assistants while seeking to retain agency through prompting and code review. When stating their acceptance criteria unprompted, they emphasize functional correctness, technical quality, and project constraints, while soft-ethical considerations, particularly those affecting end users, rarely emerge, even though developers recognize them in their own implementation choices once asked to reflect. This motivates investigating elicitation means for making developers’ preferences available to inform delegated implementation decisions.

Source: paper, Section IV: Answers #1–#3. Acceptance criteria were collected before the ethical aspects were introduced; examples of implementation choices were collected afterwards.

More survey statistics: choices and LLM use

Where is discretion exercised?

  • Error handling: 73 (70.2%); input validation: 71 (68.3%).
  • Code readability / maintainability: 71 (68.3%); data structures: 67 (64.4%); algorithms: 66 (63.5%).
  • Logging details and resource usage: 51 each (49.0%).
  • Accessibility details: 36 (34.6%); privacy details: 32 (30.8%).

Values and context

  • 44 already recognized the influence of personal values (42.3%); 45 recognized it when prompted (43.3%).
  • 68 reflected on broader consequences often or always (65.4%).
  • 30 might choose differently in another context (28.8%); 40 said “it depends” (38.5%).

What do developers use LLMs for?

  • Debugging: 86 (82.7%); generating new code: 82 (78.8%).
  • Reviewing and refactoring code: 71 each (68.3%).
  • Explaining / understanding code: 64 (61.5%); exploring alternatives: 56 (53.8%).

Percentages use 104 valid responses. Discretionary choices and LLM activities allowed multiple selections, so percentages need not sum to 100%.

RQ2 · Soft-ethical aspects

Six aspects that can manifest in code.

The aspects describe preferences over discretionary implementation alternatives. They cover both the static representation of source code and the behavior it encodes, can overlap, and apply within the space left open by mandatory requirements.

01

Fairness

Developers may prefer implementation choices that support equitable treatment across users, avoid encoding stereotypes, and differentiate users only when such distinctions are functionally relevant and justified.

Implementation ManifestationsCode can embed stereotypes or assumptions that may result in biased or differential treatment, even when the implementation is functionally correct. For example, identifiers and comments may associate stereotypical roles, behaviors, or capabilities with demographic groups, while an implementation may apply different validation, eligibility, or processing rules to users based on characteristics that are not functionally relevant.

02

Inclusiveness

Developers may prefer implementation choices that accommodate users with different abilities, languages, devices, cultural conventions, gender identities, and needs, and that avoid implicitly centering only a narrow group of users.

Implementation ManifestationsCode can encode assumptions about users’ abilities, interaction modes, linguistic and cultural conventions, gender identities, or locally specific data formats. For example, a form may restrict gender to binary options, whereas an implementation may fail to accommodate users with different accessibility needs and accept input formats that follow different national or cultural conventions.

03

Privacy

Developers may prefer implementation choices that minimize the collection, processing, storage, exposure, or sharing of personal data beyond what is functionally necessary for the system.

Implementation ManifestationsCode can collect, process, store, log, transmit, or expose user data beyond what is necessary to provide the intended functionality. For example, a form may request unnecessary demographic attributes, an application may use information that is not needed for its operation, or data may be retained, transmitted, or exposed beyond what the task requires.

04

Transparency and Explainability

Developers may prefer implementation choices that make system behavior understandable to both maintainers and end users, through readable and self-explanatory implementation logic as well as clear user-facing explanations of system behavior.

Implementation ManifestationsCode can obscure why certain inputs are required, how validation is performed, or what actions the system takes. For example, developer-to-developer understanding can be supported through clear code structure, self-explanatory identifiers, and meaningful comments, while developer-to-user understanding can be supported through explanations of why information is requested, clear labels, and informative feedback about system actions and outcomes.

05

Traceability

Developers may prefer implementation choices that make relevant actions, decisions, and responsibilities inspectable, attributable, and reviewable.

Implementation ManifestationsCode may perform actions without leaving sufficient evidence of what happened, when, and why. For example, traceability can be supported through explicit operation or submission states, meaningful error reporting, traceable validation or decision rules, audit-oriented events or logs, and mechanisms that allow users or maintainers to review relevant actions and outcomes.

06

Resource Consumption

Developers may prefer implementation choices that minimize unnecessary computation, dependencies, network traffic, storage, and runtime overhead.

Implementation ManifestationsCode may satisfy functional requirements while consuming more resources than necessary. For example, an implementation may rely on unnecessarily heavy dependencies, perform redundant computations, trigger excessive client-side updates, make repeated or unnecessary network requests, or introduce avoidable storage and runtime overhead.

Source: Table I · Considered Developer Ethical Aspects. Full descriptions and implementation manifestations reproduced from the paper.

RQ3 · Ethical profile elicitation instrument

Elicit preferences through concrete choices.

The resulting instrument uses hypothetical implementation scenarios to elicit self-reported preferences across the six aspects. Each item presents a task, two valid implementation alternatives, and a statement expressing one choice.

Insights for instrument development

Anchor answers in a familiar context

Ask developers to keep one system or application context in mind throughout. Preferences can depend on the domain, data sensitivity, target users, and resource constraints.

Make discretion explicit

Both alternatives should satisfy the intended functionality. State that requirements and legal or organizational rules leave the choice open, and clarify assumptions about implementation effort.

Use concrete, neutral scenarios

Describe actionable choices in familiar implementation terms, covering both developer-facing and user-facing concerns. Avoid wording that signals a preferred ethical answer.

Offer qualitative response options

Ask how likely developers would be to make the stated choice, from “very unlikely” to “very likely,” with a neutral midpoint. Keep numerical scores and aspect labels out of individual questions.

Balance the direction of statements

Include positively and reverse-keyed items. Reverse scoring makes higher values consistently indicate greater alignment with the corresponding aspect.

Interpret profiles in context

Use multiple items per aspect and summarize responses as a descriptive profile. Treat scores as self-reported tendencies in hypothetical situations, with context shaping their interpretation.

Evaluation outcome. Six multidisciplinary experts reviewed the instrument, and four experienced industry developers piloted it. Developers generally found the scenarios understandable and plausible; all agreed the choices could reflect individual preferences, and none reported pressure to give socially desirable answers. Psychometric validation, links to actual behavior, and effectiveness for guiding code generation remain future work.
